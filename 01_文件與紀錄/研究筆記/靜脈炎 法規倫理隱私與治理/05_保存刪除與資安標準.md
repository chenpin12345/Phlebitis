## 關鍵問題一：撤回（withdrawal）如何真正落實到 DB、檔案、快取、git 與備份？可接受且有紀錄的殘留時間是多少？

### Takeaway
台灣法規要求研究材料在研究結束或保存期限屆滿後「應即銷毀」，但「已去連結」的材料可以保留（人體研究法 §19）。研究對象可以隨時撤回同意（§14 I(6)）。PDPA §11 III 要求特定目的消失或期限屆滿時主動刪除。實務上做不到「即時從每一份備份抹除」，國際監管機關（如 ICO）接受把備份資料「put beyond use（置於無法使用狀態）」，並明確告知當事人殘留多久。

本專案可以這樣落實：線上資料當下刪除，而且全部衍生物都納入清單；備份採有上限的輪替（建議最長 90 天）；每筆受試者的照片用獨立金鑰加密，撤回時刪除金鑰（加密抹除，crypto-shredding）；另有一份不含個資的刪除帳本（tombstone / deletion ledger），還原備份時一定要重播（replay）。殘留時間要寫進同意書與 IRB 計畫書。

### Cited Findings

**A. 台灣保存與銷毀規範**
- 人體研究法 §19 原文：「研究材料於研究結束或第十四條第一項第八款所定之保存期限屆至後，應即銷毀。但經當事人同意，或已去連結者，不在此限。」最新修正日期為民國 108 年 01 月 02 日（本輪已抓取驗證）— [全國法規資料庫：人體研究法](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=L0020176) [A]
- 人體研究法 §14 I(6) 規定告知事項須包括「研究對象得隨時撤回同意之權利及撤回之方式」。§14 I(8) 是研究材料保存期限的告知事項。違反 §14 依 §24 可處新臺幣 5 萬至 50 萬元罰鍰，並得令其中止或終止研究（本輪已抓取驗證）— [全國法規資料庫：人體研究法](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=L0020176) [A]
- 「人體研究倫理審查委員會組織及運作管理辦法」規定審查會的計畫審查、查核、期中及期末報告等資料，保存至計畫結束後三年，供主管機關調閱（依搜尋摘要；條號未逐字核對）。注意這條規範的是**審查會自己的檔案**，不是研究者手上的研究資料 — [全國法規資料庫 L0020179](https://law.moj.gov.tw/LawClass/LawAll.aspx?PCode=L0020179) [A]
- 高雄榮總人體研究倫理審查委員會公告：「依據 SOP019 人委會人體研究計畫檔案保存於研究結束後 3 年，如人體研究計畫結案超過 3 年研究資料依法銷毀（除藥物試驗外）」— [高雄榮總 IRB 公告](https://org.vghks.gov.tw/erli/News_Content.aspx?n=CE2E00B93ADC201B&sms=0227F0A78C18A0A9&s=0B33C42A77F289CB) [A]（醫院 IRB 官方公告）
- 長庚 IRB SOP 024（文件的保管與調閱）：試驗結束後至少保存三年，供衛生主管機關隨時調閱；異常終止的案件檔案永久保存（依搜尋摘要）— [長庚 IRB SOP 024](https://www1.cgmh.org.tw/intr/intr1/c0040/IRBWebFile/SOP/SOP10.0/24-%E6%96%87%E4%BB%B6%E7%9A%84%E4%BF%9D%E7%AE%A1%E8%88%87%E8%AA%BF%E9%96%B1%E6%A8%99%E6%BA%96%E4%BD%9C%E6%A5%AD%E7%A8%8B%E5%BA%8F-%E9%95%B7%E5%BA%9A%E9%86%AB%E7%99%82%E8%B2%A1%E5%9C%98%E6%B3%95%E4%BA%BA%E4%BA%BA%E9%AB%94%E8%A9%A6%E9%A9%97%E5%80%AB%E7%90%86%E5%A7%94%E5%93%A1%E6%9C%83.pdf) [A]
- 陽明交大 IRB B SOP：已結案的文件存放於已結案區，至少保存三年（依搜尋摘要）— [陽明交大 IRB SOP](https://irb.nycu.edu.tw/userfiles/irbch/files/20230930115534891.pdf) [A]
- 醫療法 §70：病歷由醫療機構保存至少 7 年（未重新驗證）。**這條規範的是醫院的病歷，不是研究複本**。研究平台上的照片複本受人體研究法、PDPA 與 IRB 核准的保存期限約束，不能拿 §70 當延長保存的理由 — [全國法規資料庫：醫療法](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=L0020021) [A]
- 個人資料保護法 §11 III：個人資料蒐集的特定目的消失或期限屆滿時，應主動或依當事人請求刪除、停止處理或利用；但因執行職務或業務所必須，或經當事人書面同意者，不在此限（未重新驗證，以原文為準）— [全國法規資料庫：個資法](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=I0050021) [A]
- ICH E6(R3) GCP 已在 2025-01-06 達 Step 4（未重新驗證）。它的 essential records 保存期限交由適用法規決定，屬藥品臨床試驗的參考框架。本專案不是藥物試驗，只作參考 — [ICH E6(R3) Step 4 Final Guideline](https://database.ich.org/sites/default/files/ICH_E6%28R3%29_Step4_FinalGuideline_2025_0106.pdf) [A]

**B. 備份中的刪除（GDPR / ICO）**
- ICO 刪除權指引：「The key issue is to put the backup data 'beyond use', even if it cannot be immediately overwritten.」線上資料立即刪除時，資料會「remain within the backup environment for a certain period of time until it is overwritten」。必須向個人清楚說明資料會怎麼處理。回覆期限為「without undue delay and at the latest within one month」。頁面註明因 Data (Use and Access) Act 正在檢討（本輪已抓取驗證）— [ICO: Right to erasure](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/individual-rights/right-to-erasure/) [A]
- GDPR Art. 17（right to erasure）是撤回與刪除的歐盟基準（未重新驗證）— [EUR-Lex GDPR](https://eur-lex.europa.eu/eli/reg/2016/679/oj) [A]
- EDPB 2025 年協調執法行動（Coordinated Enforcement Framework, CEF）以刪除權為主題。本輪**未找到並驗證**它的報告內容與備份相關結論，見 Gaps。

**C. 媒體清除（NIST SP 800-88）與 SSD**
- NIST SP 800-88 Rev. 2 正式版於 **2025-09-26** 發布，取代 Rev. 1（2014）。初始公開草案（ipd）為 2025-07-21 版（本輪已搜尋驗證，CSRC 頁面歷程）— [NIST CSRC SP 800-88r2](https://csrc.nist.gov/pubs/sp/800/88/r2/final) [A]
- Rev. 2 保留 Clear / Purge / Destroy 三種方法，重心轉向建立機構層級的媒體清除計畫（sanitization program）。各類媒體的技術細節改為參照 IEEE 2883:2022。關鍵詞包括 cryptographic erase 與 secure erase（此點依 NIST 草案公告與廠商摘要；廠商摘要僅 [E]）— [NIST CSRC r2 ipd](https://csrc.nist.gov/pubs/sp/800/88/r2/ipd) [A]；[Blancco 摘要](https://blancco.com/resources/blog-nist-800-88-rev-2-updated-standard/) [E]
- 廠商摘要指出，Rev. 2 警告對現代儲存媒體（含快閃媒體）使用 Clear 有非預期洩漏的風險 — [BitRaser 摘要](https://www.bitraser.com/article/nist-800-88-r2-media-sanitization-guidelines.php) [E]（須以 NIST 原文覆核）
- Wei, Grupp, Spada, Swanson（2011）"Reliably Erasing Data From Flash-Based Solid State Drives"（USENIX FAST '11）。研究證據顯示：SSD 內建的抹除指令實作常有缺陷；**單一檔案層級的覆寫在 SSD 上不可靠**，因為 FTL 與 wear levelling 會把舊資料留在其他實體區塊。全碟覆寫通常有效但不保證（未重新驗證）— [USENIX FAST '11 Wei et al.](https://www.usenix.org/conference/fast11/presentation/wei) [C]（頂級系統研討會論文）

**D. SQLite 殘留**
- `PRAGMA secure_delete`：開啟後，被刪除的內容會以零覆寫。預設通常關閉，被刪除的資料留在 freelist pages。`FAST` 模式只在不增加 I/O 時覆寫（未重新驗證）— [SQLite PRAGMA secure_delete](https://www.sqlite.org/pragma.html#pragma_secure_delete) [A]
- `VACUUM` 會重建資料庫檔並釋放 freelist（未重新驗證）— [SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html) [A]
- WAL 模式下，變更先寫入 `-wal` 檔，checkpoint 後才回寫主檔。`-wal` 與 `-shm` 檔可能暫存舊的頁面內容（未重新驗證）— [SQLite WAL](https://www.sqlite.org/wal.html) [A]

**E. git 歷史**
- 已提交到 git 的檔案會留在歷史物件中。要徹底移除，需用 `git filter-repo` 或 BFG 改寫歷史，並強制推送與清理所有複本，已被 clone 的複本無法收回（未重新驗證）— [GitHub Docs: Removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository) [A]；[git-filter-repo](https://github.com/newren/git-filter-repo) [E]

### Inferences

**1. 法規如何組合成本專案的保存規則（本報告推論）**
- 可識別或可連結的研究材料：在 IRB 核准的保存期限（多數台灣醫院 IRB 為「結案後 3 年」）屆滿後銷毀。若沒有寫明期限，依 §19 在「研究結束」時銷毀。
- 已去連結（delinked）的材料：§19 但書允許保留，例如完全去識別、無對照表的遮罩照片或模型權重。前提是同意書與 IRB 已載明。
- 撤回同意（§14 I(6)）：預設處理為「停止使用＋刪除可連結資料」。已經用於訓練的模型權重，是否算「研究材料」仍有爭議，建議在同意書中預先說明「撤回前已完成的分析與已訓練模型不回溯」，由 IRB 核定。這點屬業界慣例，例如 GDPR Art. 17(3)(d) 的研究例外概念，但台灣的適用須由 IRB 判斷。
- 醫療法 §70 的 7 年只拘束醫院的病歷，研究平台不得援引。

**3. SQLite 具體作法（本報告推論，依 SQLite 官方文件）**
- 每次連線設定 `PRAGMA secure_delete=ON`。撤回作業後依序執行 `PRAGMA wal_checkpoint(TRUNCATE)` 與 `VACUUM`。
- 這樣只處理了**邏輯層**。SSD 的實體區塊仍可能殘留（Wei et al. 2011），所以整體仍要靠全碟加密（BitLocker；Windows 11 Home 只有「裝置加密」，不一定有完整 BitLocker）加上加密抹除，作為最終保障。

**4. Windows NTFS 的額外風險（本報告推論，依 NIST 800-88 與 Wei et al.）**
- 資源回收筒：後端刪除走 `os.remove`，不經回收筒。手動在檔案總管刪除則會進回收筒，SOP 要提醒。
- Volume Shadow Copies 與系統還原點：可能保有舊檔案版本。建議把研究資料放在不啟用系統保護的磁碟區，或定期檢查 `vssadmin list shadows`。
- SSD 的 TRIM 與 wear levelling：檔案覆寫工具（如 `cipher /w`、sdelete）在 SSD 上無法保證清除。可靠作法是全碟加密加上金鑰銷毀（NIST 的 cryptographic erase 概念），或在報廢時對整顆碟做 Purge 或 Destroy。
- Windows Search 索引與縮圖快取（thumbcache）：可能留下影像縮圖。建議把研究資料夾排除在索引之外。

**5. 加密抹除（crypto-shredding）設計（本報告推論；概念在 NIST 800-88 r2 稱為 cryptographic erase）**
- 每個 case 產生一把隨機資料金鑰（DEK，AES-256-GCM）。照片原檔、遮罩、標註與 LINE userId 都用這把金鑰加密後落地。
- 所有 DEK 用一把主金鑰（KEK）包裝，存在獨立的 `keystore.sqlite`。KEK 用 Windows DPAPI 保護，或由操作者輸入密語推導。
- 撤回時刪除該 case 的 DEK。所有備份中的對應密文就此不可讀，等於 ICO 所說的「beyond use」。
- **關鍵陷阱**：如果 keystore 也跟著資料一起進 90 天備份，加密抹除就失效。keystore 必須單獨備份，保留期短（例如 7 天）；撤回後最多 7 天，所有可解密的金鑰複本都會消失。
- 規模合理性：14 案，未來約 1,000 張照片。每案一把金鑰的管理成本很低。

**6. 備份輪替與最大殘留時間（業界慣例為 GFS；天數為本報告推論）**
- GFS（Grandfather-Father-Son）配置建議：每日備份保留 7 份，每週保留 4 份，每月保留 3 份。資料備份的最大殘留時間約 **90 天**（3 個月加上當週）。
- keystore 只保留每日 7 份，加密照片的「可讀」殘留上限是 **7 天**。
- 本報告建議在同意書與 IRB 計畫書寫明：「撤回後 30 天內完成線上系統刪除；備份中的資料最遲於 90 天內因輪替覆蓋而消失，期間以加密方式保存且無法讀取（金鑰於 7 天內銷毀）。」這與 ICO 的「清楚告知會發生什麼」一致。
- **與「不上傳第三方雲端」原則的衝突**：若有人提議 OneDrive、Google Drive 或任何雲端異地備份，即違反專案原則。替代方案是兩顆輪替使用的 **加密外接硬碟**（BitLocker To Go 或 VeraCrypt），一顆放在院內上鎖處作為異地，一顆在本機旁。外接碟同樣遵守 90 天輪替。報廢時依 NIST 800-88 做 Purge 或 Destroy。注意：Windows 11 Home 預設沒有 BitLocker To Go 的加密功能，可改用 VeraCrypt。

**7. 刪除帳本（tombstone / deletion ledger），還原時重播（本報告推論）**
- 帳本是 append-only 的檔案，例如 `deletion_ledger.jsonl`，每列內容為：
  - `{ts, ledger_seq, case_uuid, reason: "withdrawal|retention_expiry|error", artifacts: ["photo","masked","thumb","gradcam","features","labels","eval","line_map"], counts, operator_role, key_destroyed: true, prev_hash}`
- `case_uuid` 必須是系統內部隨機 UUID，**不得**是病歷號、姓名、LINE userId 或它們的雜湊（低熵識別碼的雜湊可以被暴力反推）。
- `prev_hash` 形成雜湊鏈，可偵測竄改。
- 帳本本身不含個資，可以長期保存，作為 IRB 稽核證據。
- **還原程序**：從任何備份還原後，必須先重播帳本：讀取所有 tombstone，刪除已撤回 case 的殘留後，服務才能啟動。可以在 FastAPI 的 startup 加入檢查：若帳本序號大於 DB 中已套用的序號，就拒絕啟動，直到重播完成。
- 帳本要放在備份輪替之外，也要另外寫到外接碟，否則還原舊備份時會連帳本一起倒退。

**8. git（本報告推論）**
- 最好的作法是照片、標註、embedding、評估逐例輸出與 DB **一律不進 git**。git 只存程式碼與不含資料的設定。
- 建議在 pre-commit hook 擋下 `*.jpg/*.png/*.npy/*.sqlite/labels/*.txt`。
- 若曾經提交，必須用 git filter-repo 改寫歷史，並處理全部複本，包括「04_備份」中的 .git 鏡像。

## 關鍵問題二：單機研究平台「現在」必須具備哪些資安控制？（含 ISO、台灣法規、OWASP、模型檔案安全、LINE、對外暴露）

### Takeaway
本專案不受台灣資通安全管理法直接拘束，因為它不是公務機關，也不是被指定的特定非公務機關。合作醫院可能受拘束，並會透過契約把要求轉嫁過來。現在最該做的是一小組高效控制：
- LINE webhook 的 HMAC 簽章驗證與秘密管理
- admin 只綁 localhost
- 全碟或資料加密與加密備份
- 只收 safetensors，並鎖定雜湊
- 依賴套件盤點（對應 OWASP Top 10:2025 A03 Software Supply Chain Failures）
- 存取與刪除日誌
- 對外暴露路徑的 TLS 終止點評估

完整的 ISO/IEC 27001 認證、ASVS L3 與 27701 認證都可以延後。

### Inferences

**1. 法規適用性（本報告推論）**
- 資通安全管理法拘束的是公務機關與特定非公務機關（含關鍵基礎設施提供者）。部分醫院（如醫學中心）可能被指定為關鍵基礎設施提供者，但本研究平台本身不是。實際影響是合作醫院會透過資料提供契約或 IRB 條件，要求平台做到某些控制，例如加密、存取紀錄與資安事件通報。
- 醫療機構電子病歷製作及管理辦法：本平台不製作也不管理病歷，**不適用**。
- 衛福部的醫院資安要求（如醫院評鑑的資安項目、醫療機構資安指引）：本輪**未找到並驗證**現行條文，見 Gaps。

- 5.34 隱私與 PII 保護
- 8.10 資訊刪除（information deletion）：直接對應撤回
- 8.11 資料遮罩（data masking）：對應遮罩照片

- 7.10 / 7.14 儲存媒體與設備報廢

**3. ASVS 5.0 套用方式（本報告推論；章節名稱依 ASVS 5.0 結構，須對照官方 PDF 逐章確認）**
- 公開的 LINE webhook 端點：目標 **L2**。重點章節：
  - 輸入驗證與編碼
  - 檔案處理：上傳影像的型別與大小限制，用 Pillow 重新編碼並去除 EXIF/GPS
  - API 與 Web Service
  - 加密與秘密管理
  - 安全通訊（TLS）
  - 日誌與錯誤處理
  - 設定
  - webhook 簽章：先驗章，失敗回 401，並在比對時使用常數時間比較（`hmac.compare_digest`）
- 只綁 localhost 的管理介面：目標 **L1 到 L2**。重點：
  - 綁 `127.0.0.1`，不綁 `0.0.0.0`
  - 防 CSRF 與 DNS rebinding：檢查 Host/Origin 標頭，否則其他網頁可以從瀏覽器打 localhost API
  - 存取控制：單一操作者也要有本機登入或 token
  - 安全標頭
- 醫療資料理論上可以要求 L3，但對單機原型屬於延後項目。

**4. ML 與模型供應鏈（業界慣例加本報告推論）**
- 只接受 `.safetensors`。拒絕 `.pt/.pth/.bin/.pkl/.ckpt`，即使副檔名改過，也要檢查 magic header。不要以 `torch.load(weights_only=False)` 載入任何外部檔案。
- 建立模型登錄表（model registry），記錄來源、SHA-256、授權、匯入人與日期。匯入後鎖定雜湊，每次載入都比對。
- safetensors 只保證權重檔不會執行程式碼，**不保證**模型沒有後門或沒有被投毒（ML10 / ML02）。外部模型必須在固定驗證集上重新評估，並由人工核准，才能使用。這也符合「不自動訓練、不自動部署」的專案原則。
- 資料投毒（ML02）：LINE 公開來源的照片有可能被惡意提交。建議設獨立的「公眾來源」標記與人工審核，預設不直接進入訓練集。
- 輸入操弄（ML01）：公開端點只收照片、不即時回傳模型判讀時，風險較低。若要回傳判讀結果，則要評估對抗樣本與濫用風險。

**5. 對外暴露與「不上傳第三方雲端」的衝突（本報告推論）**
- LINE 本身就是第三方。使用者傳的照片先存在 LINE 伺服器，這一段無法避免，必須在同意說明中揭露。
- Cloudflare Tunnel 或 ngrok 的 TLS 通常在供應商邊緣終止，第三方會看到照片明文（雖然只是轉送，不是儲存）。這與「研究照片不上傳第三方雲端」的原則**有張力**。不過照片取回其實是本機主動以 HTTPS 呼叫 LINE content API，不經 tunnel；經過 tunnel 的只有 webhook 事件 JSON（含 message ID、userId 與文字訊息）。
- **建議設計**：webhook 只接事件，照片一律由本機用 `GET content` 直接從 `api-data.line.me` 拉取。照片就不會經過 tunnel 供應商，tunnel 只看到事件中繼資料。
- 替代方案：
  - 在院內自有的固定 IP 主機上自行終止 TLS（需處理憑證與防火牆）。
  - 使用支援端到端 TLS passthrough 的 tunnel 方案（需另外查證供應商是否支援）。
- 這一點應寫入風險評估，並交由 IRB 知悉。
