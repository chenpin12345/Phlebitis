### 1.4 只保留岡山高醫的影響

這不是功能互斥，但會改變成績能代表的意義：

- **好處**：來源捷徑的嫌疑來源整批移除；每張照片都有病人分組；資料回到決策總報告的基準（14 位、56 張、9 張正常），報告的階段規劃可以直接沿用。
- **代價**：正常照片從 28 張降到 9 張，只來自 3 位病人。分病人交叉驗證時每折大約只有 1 位正常病人，重複切分對正常組的幫助也有限。
- **處理**：#10、#14、#15 全部照做，但切分時每折至少要有 1 位正常病人。二分類的正常誤報率會有很寬的信賴區間，報告會寫成「流程驗證」，不當成效結果。要改善只能收更多正常病人。
- **成績預期**：新成績很可能比 10/31 差，這是移除捷徑後的合理結果。

**待你刪除的資料夾**：`03_模型與影像資料/待你刪除/` 放 37 張照片、`archive/legacy/YOLODataset`、YOLO 基礎權重與 `selected/`，附 `README.md` 與清單。內容確認沒問題後，由你手動刪除。

## 6. 每個里程碑的共通規則

1. 開始前確認工作台閒置；動資料前備份，並留前後檔數與雜湊。
2. 每個小節一個 commit，只在本機，不加 attribution，不推遠端；里程碑結束打標籤（`m1`、`m2`…）。
3. 里程碑結束依序跑：`scripts\check.ps1`、6 套瀏覽器回歸（只用 8877 fixture，每套前重啟）、`python -m src doctor`、正式工作台畫面檢查。
4. 運行問題直接修，列入報告 #63 起（D5）。
5. 下列規則**不因 D4、D5 放寬**：不自動訓練、不自動啟用模型、不真的發 LINE、外部來源唯讀、永久刪除只透過垃圾桶、建議須人工確認。碰到這些會停下來問你。
6. 測試只用 `workbench_fixture.configure()` 的隔離根目錄；新資料庫讀寫走 `jobs.db()`；UI 遵守 `style.css` 的 token 規則。
7. 寫完里程碑報告就停下，等你說繼續。

## 10. 驗證方式與風險

**端對端驗證**：
- 每階段：`scripts\check.ps1`、6 套回歸、`doctor`、正式工作台畫面。
- M0：`git log -p` 全掃不到真實病歷號。
- M1：比對資料夾雜湊，掃描新照片 0 張。
- M2：`test_no_yolo.py`、乾淨 venv 安裝、遷移結果 75／18／28。
- M2.5：真實資料的來源檢查結論；移除後 56／0／28、14 位病人。
- M4：新成績與舊成績並列，寫明差異原因。
- M5–M5.5：假 LINE 伺服器模擬完整流程。
- M6：撤回演練。
- M7：從 `setup.bat` 全新安裝到啟動。

| 風險 | 對策 |
|---|---|
| 改寫 git 歷史出錯 | 先存 bundle；驗證內容只差遮罩；舊備份由你確認後才刪 |
| 舊截圖裡有真實畫面 | M0 逐張檢查，有就從歷史移除 |
| 遷移改壞 manifest | 先備份、重跑無變化、75 張標籤逐筆比對 |
| 移除 37 張時誤傷岡山高醫照片 | 預覽清單、只動 `IMG_xxxx` 且來源為 YOLODataset 的列、56 張標籤逐筆比對 |
| 正常病人太少，二分類不穩定 | 照實報告為流程驗證；要改善只能增加正常病人 |
| 移除 YOLO 時誤傷分類 | 分類測試全程保留；每小節一個 commit，可單獨退回 |
| 舊工作與報告打不開 | 專門測試舊紀錄讀取 |
| 新成績比舊成績差 | 這是修正捷徑後的預期結果，照實報告，不調到好看 |
| 撤回有遺漏 | 用雜湊全專案掃描驗證 |
| 備份加密後金鑰遺失 | 預設關閉；開啟時產生復原金鑰；舊備份組保留到你確認 |
