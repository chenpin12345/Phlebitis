────────────────────
八、每項容量及可釋放容量
────────────────────

目標：
垃圾桶每筆資料都能看見容量資訊與刪除後可釋放多少，
但必須忠實反映計算能力及限制。

A. 容量定義

至少區分：
1. 資料容量：
   該項受管理內容的邏輯大小，必要時分成檔案與資料庫內容。
2. 獨占可清理檔案容量：
   已确认歸屬本項、未被保護或其他資源使用的檔案大小。
3. 預估可釋放磁碟空間：
   本次具體刪除計畫預期回收的空間。
4. 仍保留容量：
   共用、受保護、必要追溯或不在此次範圍內的內容。

畫面可使用簡潔主欄位，詳細定義放入展開區或提示。
不可把上述不同概念混用。

B. 計算規則

1. 使用檔案系統及真實資料來源計算。
2. 容量顯示人類可讀單位，明細保留 bytes。
3. 顯示計算時間與狀態：
   計算中／已計算／估計值／過期／無法計算。
4. 不可讀或未知不得顯示成 0。
5. 已存在的工作輸出、模型權重、checkpoint、
   日誌及報告按實際歸屬整理，不依名稱猜測。
6. 歷史報告或快照不在此次刪除範圍時，不算入可釋放容量。
7. 同一路徑或實體檔案被多項引用時不得重複計算。
8. 批次總容量需對完整選取集合去重，不能直接相加每列數字。
9. 共用檔案只有在所有相關引用都已正確處理時，才能計入可清理部分。
10. 對硬連結、符號連結、Windows junction／reparse point
    採安全策略，不沿連結遞迴刪除外部檔案。
11. 無法確認實體歸屬或其他連結時，顯示限制並排除永久刪除。
12. 不把工作目錄、模型目錄之外的備份或副本算成已刪除。
13. 檔案邏輯大小與磁碟配置大小不同時，標明估計口徑。
14. 不宣稱具備作業系統層級的精確回收值，除非確實量測得到。

C. SQLite 特別處理

1. 操作稽核與工作資料庫列的內容大小，可顯示有明確口徑的估計值。
2. 不把序列化 JSON 的長度當成真實磁碟占用。
3. 永久刪除資料列通常先產生資料庫內部可重用空間，
   不保證資料庫檔案立即縮小。
4. 畫面需清楚顯示：
   「資料庫內容約 X；立即可釋放磁碟空間不保證，
   刪除後空間可由資料庫重用。」
5. 無可靠方法把資料庫頁面分攤到單筆時，
   顯示不可逐筆精確計算，不捏造數字。
6. 不把整個 SQLite、WAL 或 SHM 檔案當成單筆稽核的附件刪除。
7. 不在每次單筆刪除後自動執行 VACUUM。
8. 本次如不實作資料庫檔案壓縮，明確告知限制，不影響列刪除功能。
9. 不以刪除資料庫檔案達成容量回收。

D. 使用體驗與效能

1. 提供重新計算容量。
2. 大型目錄掃描避免阻塞管理 API。
3. 可快取結果，但提供計算時間及失效策略。
4. 永久刪除前必須重新檢查，不能只用快取。
5. 不在每次輪詢重複掃描所有權重。
6. 容量無法計算時，列出具體原因；
   不因暫時無法取得數字就從垃圾桶隱藏該項目。

九、永久刪除只能從垃圾桶執行
────────────────────

A. 操作範圍

1. 所有一般頁面只提供移至垃圾桶。
2. 永久刪除按鈕只出現在垃圾桶。
3. 後端要求目標目前仍在垃圾桶，不能直接永久刪除正常資源。
4. 不只靠按鈕位置保護，需使用後端刪除預覽與提交流程。
5. 不依赖 Referer 或頁面路徑作為安全保證。
6. 保留現有 CSRF、本機管理限制及有效會話機制。
7. 本次不新增任意路徑刪除 API。

既有 LINE 結果到期與資料撤回屬原本必要生命週期，
不應因垃圾桶而失效。
但對本次受管理的工作、模型及稽核，其他管理頁不可提供
繞過垃圾桶的手動永久刪除入口。

B. 刪除預覽

按下永久刪除後，先由後端產生預覽，包含：
- 目標類型與 ID。
- 項目名稱。
- 實際要刪除的受管理檔案及資料庫內容。
- 保留內容。
- 關聯資源。
- 影響、警告及阻擋原因。
- 資料容量。
- 預估可釋放容量。
- 共用或受保護容量。
- 預覽時間及有效狀態。

大型清單可分組與按需展開，不必一次列出全部檔案。
預覽本身不得執行刪除。

C. 確認彈窗

1. 彈窗明確標示「永久刪除後無法由垃圾桶還原」。
2. 顯示對象、數量、範圍、容量及影響。
3. 預設焦點放在安全操作，Enter 不應意外觸發破壞性按鈕。
4. 取消及關閉不產生刪除副作用。
5. 涉及模型權重、checkpoint、批次或重要历史時，
   要求輸入項目名稱或明確確認文字。
6. 不用固定容量門檻代替相依性判斷。
7. 對不同項目的具體影響分組說明。
8. 計算中、預覽失效或有硬性阻擋時，不能提交。
9. 提交中防止重複點擊。
10. 避免巢狀彈窗，支援鍵盤與焦點返回。

D. 影響分級與工程師決策

第一類：可直接確認的安全清理
- 已終止、未被使用的獨占產物。
- 顯示一般不可還原警告及容量。

第二類：可由工程師接受的歷史影響
例如：
- 刪除 checkpoint 後不能從該點續訓。
- 刪除日誌後無法查看完整訓練過程。
- 刪除權重後，保留的歷史報告仍可讀，
  但不能用該版本重新推論。
必須列出具體後果，經加強確認後才允許。

第三類：必須先處理的阻擋
例如：
- LINE 或本地目前使用中的模型。
- queued／running／cancelling 工作需要的檔案。
- 模型回復仍直接依賴的版本。
- 無法確認的共用檔案。
- 正在寫入或狀態不確定的資料。
- 程式碼、環境、設定、金鑰、資料庫本體與系統必要檔案。

第三類不能以「我了解風險」無條件覆蓋。
顯示工程師可採取的前置動作，例如：
先停止工作、切換有效模型、明確處理回復引用，
再重新產生刪除預覽。

不能自動停止 LINE、自動切換模型或暗中刪除其他依賴。

E. 提交前再次驗證

1. 預覽與提交綁定具體 ID、類型、版本及刪除範圍。
2. 可使用伺服器保存的短效預覽 ID 或等價機制。
3. 不能信任前端自行提交的檔案路徑、容量或「無依賴」結論。
4. 提交時重新確認垃圾桶狀態、引用及檔案身分。
5. 若預覽後有新工作、新引用或內容變更，拒絕舊計畫並要求刷新。
6. 處理檢查與使用之間的競態，核對鎖定順序。
7. 在資源進入永久刪除流程後，阻止新工作取得它。
8. 相同刪除請求使用冪等機制，重送不重複執行或誤刪其他項目。
9. 不在長時間刪除大型檔案時無限制占住資料庫寫入交易。

F. 執行與範圍

1. 只刪除預覽計畫核准的內容。
2. 不由前端傳任意目錄給後端遞迴刪除。
3. 執行前檢查解析後的真實路徑仍位於允許根目錄。
4. 不跟隨連結刪除外部資料。
5. 不刪共享檔案或未列入計畫的副本。
6. 不自動連帶刪除評估報告、快照或原始圖片。
7. 若只能清理部分內容，彈窗及完成結果必須明確說明；
   不把部分成功稱為整個項目永久刪除。
8. 當歷史報告需要最小來源資訊時，保留必要的刪除摘要或 tombstone，
   不保留假裝仍可執行的模型。
9. 如果保留內容仍需要原工作設定，先確保有可靠追溯來源，
   再刪除原工作產物。
10. 不因刪除 jobs 資料列而移除冪等防護；必要時保留最小映射。
11. 稽核永久刪除須維持穩定 ID 規則，不導致舊 ID 被新事件重用。
12. 不直接刪除 SQLite 資料庫檔案。

十、批次刪除、失敗恢復與結果
────────────────────

A. 批次操作

1. 批次範圍固定為明確選取 ID，不以執行時重新套用篩選條件擴張。
2. 顯示總數、各類型數量與去重後容量。
3. 有阻擋項目時列出原因，不默默跳過。
4. 若允許只刪除可處理項目，必須明確展示縮小後範圍，
   再由使用者確認。
5. 執行中顯示進度及逐項結果。
6. 不假裝多檔案實體刪除具備全部可回滾的交易。
7. 如提供停止操作，應說明只能停止尚未處理項目，
   已刪除內容不能撤銷。

B. 執行紀錄與重啟恢復

1. 建立持久的刪除操作紀錄，避免服務重啟後遺失進度。
2. 狀態至少能區分準備、執行中、完成、部分失敗與待檢查。
3. 檔案占用、權限不足、路徑變更、磁碟錯誤須正確回報。
4. 中斷後不自動還原成可正常使用的資源。
5. 重試只處理原計畫中尚未完成且仍合法的部分，
   不擴大範圍。
6. 已刪檔案再次不存在，可依操作紀錄判斷是否已完成；
   不能把所有 FileNotFound 都無條件當成功。
7. 清理過程有錯誤時保留必要診斷，不記錄金鑰或敏感圖片內容。

C. 完成結果與容量回報

至少顯示：
- 操作 ID 與時間。
- 成功、失敗及未處理項目。
- 已確認移除的檔案數量。
- 已刪除檔案的邏輯容量。
- 可可靠取得時的磁碟回收資訊。
- 尚保留的內容及原因。
- 失敗原因與可採取的下一步。

注意：
1. 不把全磁碟可用空間的前後差值，
   當成此次操作精確釋放量，因為其他程序可能同時寫入。
2. 無法量測實際配置空間时，明確標示估計值。
3. SQLite 列刪除與檔案縮小分開說明。
4. 操作紀錄本身也占空間，不宣稱必然百分之百等同預估值。
5. 保留最小必要刪除摘要，不能宣稱備份、外部副本或 LINE 平台內容已同步刪除。

D. 暫不提供

- 自動清空。
- 定時永久刪除。
- 沒有預覽的一鍵清空。
- 無條件 force=true 繞過保護。
- 沒有相依性檢查的全目錄刪除。
